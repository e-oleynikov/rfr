# UI-тесты

Требуются JDK 25, MySQL и запущенные `rfr-auth`, `rfr-api`, `rfr-gql-client`.

Перед первым запуском и после обновления Playwright установите Chromium из корня:

```bash
./gradlew :rfr-e2e:installPlaywright
```

Задача использует версию Playwright из `rfr-e2e/build.gradle`, требует доступа
к серверу загрузки браузеров и не выполняется автоматически перед тестами.

Для локальной MySQL из Docker Compose пароль уже задан по умолчанию.
Для другой БД переопределите `RFR_DB_PASSWORD`, как описано в разделе [«Настройки тестов»](#настройки-тестов).

Из корня репозитория:

```bash
./gradlew e2eTest
```

Корневая задача запускает только `:rfr-e2e:test`, сохраняя его настройки JUnit,
Allure и параметры `rfr.*`. Она не запускает серверы, БД или тесты бэкенд-модулей
и не изменяет поведение `build`.

Для отдельного класса используйте прямую тестовую задачу:

```bash
./gradlew :rfr-e2e:test --tests '*RegistrationTest'
```

`RegistrationTest` регистрирует уникального пользователя через UI,
входит с его данными и проверяет логин в профиле. Данные создаёт `RandomDataUtils`,
очистку выполняет `@AfterEach`; до регистрации учётной записи в БД нет.

`LoginTest` проверяет вход с заранее созданной учётной записью:

```bash
./gradlew :rfr-e2e:test --tests '*LoginTest'
```

`LoginNegativeTest` проверяет неверный пароль и несуществующего пользователя.
В обоих случаях ожидается `Bad credentials` в `.form__error` на странице входа.
Для детерминированного текста Spring Security тесты задают `Accept-Language: en-US`.
Второй сценарий не создаёт пользователя и проверяет отсутствие записи в БД.

```bash
./gradlew :rfr-e2e:test --tests '*LoginNegativeTest'
```

Тестовый метод принимает `@User TestUser user`. На классе нужно зарегистрировать
`@ExtendWith({UserExtension.class, BrowserExtension.class})`.
`@User` всегда означает создание пользователя в auth-БД, без режима «только данные».

Параметры `@User(friends = 1, incomingInvitations = 1, outcomeInvitations = 1)` передаются в `UserRequest`.
Все счётчики по умолчанию равны `0`; отрицательные значения запрещены.
`new UserRequest(annotation).fixture()` собирает цепочку без записи в БД:
`SingeUserFixture` оборачивается в `UserWithRelationsFixture(origin, relation, count)`
для `Relation.FRIEND`, `Relation.INCOME_INVITATION` и `Relation.OUTCOME_INVITATION`.
Декораторы добавляются только для ненулевых счётчиков. Расширение сохраняет
цепочку в Store перед вызовом `create()`.
Декораторы создают указанное количество дополнительных пользователей и связи:
`ACCEPTED` для друзей, `PENDING` от отправителей к основному пользователю для
входящих приглашений и в обратном направлении для исходящих.
`Relation` определяет создание связи и добавление пользователя в соответствующий список `TestUser`.
Для нового типа связи достаточно нового значения enum и подключения счётчика в `UserRequest.fixture()`.
`user()` всегда возвращает основного пользователя.
Общий жизненный цикл декораторов находится в `UserRelationshipFixture`.
Очистка закрывает дополнительных пользователей и вложенную фикстуру даже при
ошибке одного из удалений; ошибки сохраняются, включая suppressed exceptions.
Общий механизм очистки — `utils/TearDown`: `with(action)` регистрирует действие,
`withEach(items, action)` регистрирует действия для текущего снимка элементов,
`run()` выполняет их по порядку. `RuntimeException` не прерывает остальные действия:
первая ошибка выбрасывается после очистки, последующие добавляются как suppressed.
Декоратор обходит дополнительные фикстуры в обратном порядке и удаляет из списка
только успешно закрытые, затем закрывает вложенную фикстуру. При повторном `close()`
новая цепочка получает оставшиеся ресурсы. Сам `TearDown.run()` повторяет все
зарегистрированные действия при каждом вызове.

`ProfileTest` проверяет сохранение имени, фамилии, страны Germany и аватара после
перезагрузки, а также возврат сохранённых значений по Reset. Страны фиксированы,
изображения находятся в `src/test/resources/images/`. Каждый сценарий использует
отдельного пользователя через `@User`.

```bash
./gradlew :rfr-e2e:test --tests '*ProfileTest'
```

`page/ProfilePage` отделяет заполнение данных, выбор страны, загрузку аватара,
Save, Reset и проверки. `clickSave()` дожидается ответа GraphQL `UpdateUser`,
чтобы последующий reload не опередил сохранение.

Page Object скрывают локаторы, действия и ожидающие проверки Playwright.
`BrowserExtension` передаёт тесту `Page` с отдельным браузерным контекстом.
`UserExtension` обрабатывает только параметры `TestUser` с аннотацией `@User`.
`UserFixture` — интерфейс, расширяющий `AutoCloseable`, с методами `create()`,
`user()` и `close()`. Текущая реализация — `SingeUserFixture`.
Для каждого параметра сохраняется отдельная фикстура
в `ExtensionContext.Store` тестового метода. `UserFixture.create()` создаёт
пользователя и права `read`/`write` в auth-БД, расширение передаёт данные в параметр.
После теста и закрытия браузера JUnit 6 автоматически вызывает `UserFixture.close()`,
который удаляет учётную запись и API-профиль. Ручного `afterEach` в расширении нет.
Фикстура сохраняется до вызова `create()`, поэтому закрывается и при ошибке подготовки.
Повторный `close()` после успешного удаления ничего не делает.
Несколько параметров `@User` получают разные фикстуры и учётные записи.
Не отключайте настройку JUnit `junit.jupiter.extensions.store.close.autocloseable.enabled`.
Пароль кодируется тем же `PasswordEncoderFactories.createDelegatingPasswordEncoder()`,
что и в auth-сервисе. Без связей API-профиль создаёт приложение при первом входе.
Для связей декораторы заранее создают недостающие API-профили со страной `ru`,
как при первом входе в приложение.
Создание и очистка находятся в `TestUserRepository`.

API удаления пользователя отсутствует, поэтому очистка работает через Spring JDBC
без запуска Spring-контекста. В пакете `data/db`:

- `Databases.AUTH` и `Databases.API` содержат собственные `DataSource` и transaction manager.
  Оба используют настройки MySQL из `TestConfig`, выбирая соответствующий каталог.
- `Jdbc.getClient(database)` возвращает Spring `JdbcClient`.
- `Jdbc.inTransaction(database, client -> { ... })` выполняет действия в транзакции
  выбранной БД с автоматическим rollback при ошибке.
- `Jdbc.loadSql(resourcePath)` читает SQL из classpath в UTF-8.

SQL инкапсулирован в небольших immutable-объектах `data/db`: `AuthAccount`,
`Authorities`, `Profile`, `FriendShip`, `Invitation`, `Friendships`, `Invitations`.
Конструктор принимает `JdbcClient` и логин пользователя либо логины пары;
объект не кеширует состояние БД. Методы `create()`, `delete()`, `exist()` работают
с одной сущностью. Для `AuthAccount.create(password)` пароль передаётся только
на время создания и кодируется внутри объекта, не сохраняется в его полях.
`Friendships` и `Invitations` предоставляют `delete()`, `exist()` и `list()`;
`list()` возвращает неизменяемый снимок `Relationship`. Создание связей выполняют
объекты одной пары, без неиспользуемого массового API.
Дружба симметрична, а `Invitation` учитывает отправителя и адресата.
Все `delete()` проверяют тестовый формат логина; удаление одной пары проверяет оба.
`TestUserRepository` координирует эти объекты и передаёт им общий клиент транзакции.
Объекты сами не открывают транзакции и не переключают соединение или схему.

`./gradlew :rfr-e2e:test --tests '*DatabaseObjectsTest'` проверяет операции объектов,
направление связей, защиту удаления и откат очистки обеих схем в одной транзакции.

Все запросы находятся в `src/test/resources/sql/`, параметры передаются по именам.
Для подготовки связей используются SQL в `sql/api/`:

- `create-friendship.sql` создаёт связь `ACCEPTED` между `:requesterUsername` и `:addresseeUsername`.
- `create-invitation.sql` создаёт приглашение `PENDING` от `:requesterUsername` к `:addresseeUsername`.
- `delete-friends.sql` удаляет все связи `ACCEPTED` пользователя `:username` в обоих направлениях.
- `delete-invitations.sql` удаляет все входящие и исходящие приглашения `PENDING` пользователя `:username`.

Оба пользователя должны уже существовать в API-БД. Создание связи с собой,
повторной пары или связи с отсутствующим пользователем завершается ошибкой БД.
Запросы удаления связей не удаляют учётные записи. `TestUserRepository.delete()`
проверяет формат тестового логина и удаляет его дружбу и приглашения перед
удалением профиля, прав и учётной записи в общей транзакции.

`./gradlew :rfr-e2e:test --tests '*UserFixtureTest'` проверяет декораторы на MySQL:
счётчики, направление приглашений, очистку, изоляцию и частичный сбой подготовки.
Для этих проверок браузер и запущенные бэкенды не нужны; нужны обе схемы с миграциями.

`./gradlew :rfr-e2e:test --tests '*FriendshipTest'` запускает три UI-сценария:
отображение двух друзей и трёх входящих заявок из `@User`, отправку заявки
пользователем без связей и создание дружбы через отправку и принятие заявки.
Два пользователя работают в отдельных браузерных контекстах. Данные очищаются
автоматически при закрытии Store, без ручного вызова `UserFixture.close()` в тестах.
Для этих сценариев нужны MySQL, оба бэкенда, интерфейс и Chromium.

Очистка выполняется через один клиент `AUTH`, а SQL явно указывает обе схемы:
это сохраняет общую транзакцию на одном соединении. Переключение на клиент другой
БД внутри callback не включит его в ту же локальную транзакцию.

При очистке
профиль в `rangiffler-api`, права и пользователь в `rangiffler-auth` удаляются
в одной транзакции. Нужен доступ к обеим схемам на одном сервере MySQL.
Удаляется только точный логин текущего запуска с префиксом `ui_registration_`.
До регистрации проверяются доступ к БД и отсутствие такого логина;
после удаления проверяется отсутствие пользователя в обеих схемах.
Ошибка очистки приводит к неуспешному результату теста.

`RandomDataUtils` генерирует уникальный логин, пароль и `TestUser` средствами
стандартной Java, без дополнительных библиотек. Модель `TestUser` хранит данные.
В `TestUser` доступны неизменяемые списки `friends()`, `incomingInvitationSenders()`
и `outcomeInvitations()` с данными созданных друзей, отправителей входящих заявок
и получателей исходящих приглашений, включая данные для входа.
Конструктор копирует списки через `List.copyOf()`; конструктор из логина и пароля
по умолчанию задаёт пустые списки. Декоратор добавляет пользователя в новый record
только после успешного создания связи, сохраняя списки вложенной фикстуры.
Списки отражают подготовленные прекондишены и не обновляются после действий в UI
или очистки БД. Ресурсами и их очисткой владеют фикстуры, а не record.

## Настройки тестов

### Проверка UserExtension через JUnit Engine

`./gradlew :rfr-e2e:test --tests '*UserExtensionTest'` запускает 13 проверок
через `junit-platform-testkit` с версией из JUnit BOM. Нужна локальная MySQL
с обеими схемами и миграциями; браузер и запущенные бэкенды для них не нужны.
Проверки используют настоящий `UserExtension` и реальные фикстуры без подмены фабрики.

Классы-мишени находятся в `UserExtensionTargets` и помечены составной аннотацией
`@EngineTarget` с `@EnabledIf`. Она разрешает выполнение только при configuration
parameter `rfr.user-extension.testkit.enabled=true`, который задаёт внутренний
EngineTestKit-запуск. Глобальное свойство JVM не меняется. Отдельная проверка
запускает каждую мишень без параметра и подтверждает, что она пропущена.

`TestReporter` фиксирует `prepared`, `beforeEach`, `test`, `afterEach`,
`beforeStoreClose` и данные пользователей без паролей. Тестовый `LifecycleProbe`
читает фикстуры из Store по namespace `UserExtension` и индексу параметра:
это осознанная проверка контракта хранения. Он не создаёт и не закрывает фикстуры.
События Engine проверяются обычными JUnit assertions и публикуются внешним
`TestReporter`. После завершения `execute()` проверяется отсутствие учётных записей,
прав, профилей и связей в БД, затем публикуется событие `storeClosed`.

Покрыты обычный пользователь, списки друзей и заявок, несколько параметров,
падение тела теста, ошибка второго параметра после создания первого пользователя,
неверный тип и отрицательные счётчики, отсутствие `@User` и совместимость с
встроенными parameter resolvers JUnit. При ошибке `BeforeEachCallback` метод
`@AfterEach` не вызывается; `AfterEachCallback` всё ещё наблюдает данные перед
закрытием Store. Ошибки внутри `UserFixture.create()` и ошибки самой очистки
этими EngineTestKit-сценариями искусственно не вызываются.

### Статические пользователи

`@StaticUser TestUser` самостоятельно подключает `UsersQueueExtension` и предназначена
для среды, где создать нового пользователя нельзя. `StaticUserFixture` берёт запись
из единой потокобезопасной очереди JVM на три пользователя; по умолчанию ожидает
до 5 секунд, затем сообщает об исчерпании пула. Фикстура сохраняется в Store до
получения пользователя и возвращает только свою запись при закрытии Store, в том
числе после упавшего теста. Повторный `close()` не дублирует запись в очереди.
Фикстура не создаёт и не удаляет данные в БД. Текущие пары демонстрационные:
заводить их в стенде не нужно, для браузерных сценариев используется `@User`.

`./gradlew :rfr-e2e:test --tests '*UsersQueueExtensionTest' --tests '*StaticUserFixtureTest'`
проверяет повторное использование трёх записей четырьмя тестами, возврат после
падения, таймаут, повторное закрытие и получение освободившейся записи другим потоком.
После каждого теста `UsersQueueExtensionTest` проверяется доступность всего пула.
Этим проверкам не нужны БД, бэкенды или браузер.

### Вкладки People

`./gradlew :rfr-e2e:test --tests '*TabTest'` запускает 12 сценариев из `test/people`:
состав и элементы управления строкой, фильтрация типов связей, изоляция владельцев
и пустое состояние для каждой из трёх вкладок. Кнопки проверяются без нажатий.
Счётчики `@User` не превышают 1; все связанные пользователи создаются данным тестом.

### Параметры окружения

Все настройки читает `config/TestConfig`: system property → переменная окружения →
константа fallback. Например, `rfr.front.url` → `RFR_FRONT_URL` → `http://localhost:3001`.
Префикс system properties — `rfr.`, ENV — `RFR_`; точки в ключах заменяются на `_`.
Gradle передаёт свойства `rfr.*` в тестовую JVM; тот же формат работает при запуске из IDEA.
При прямом запуске из IDEA указывайте свойства в VM options, переменные окружения —
в Environment variables конфигурации запуска. `TestConfig` не читает `.env` интерфейса.
Эти параметры не изменяют конфигурацию запущенных сервисов.

| System property | ENV | Fallback |
| --- | --- | --- |
| `rfr.front.url` | `RFR_FRONT_URL` | `http://localhost:3001` |
| `rfr.auth.url` | `RFR_AUTH_URL` | `http://localhost:9001` |
| `rfr.headed` | `RFR_HEADED` | `false`; `true` открывает видимый Chromium |
| `rfr.db.url` | `RFR_DB_URL` | `jdbc:mysql://localhost:3306/?useSSL=false&allowPublicKeyRetrieval=true&connectTimeout=5000&socketTimeout=10000` |
| `rfr.db.user` | `RFR_DB_USER` | `root` |
| `rfr.db.password` | `RFR_DB_PASSWORD` | Локальный тестовый пароль из `docker-compose.yml` |

Тайм-аут подключения к БД по умолчанию — 5 секунд, чтения — 10 секунд.
Каталоги `rangiffler-auth` и `rangiffler-api` выбирает `data/db/Databases`;
учётной записи нужен доступ к обеим схемам на одном сервере MySQL.
Пароль по умолчанию совпадает с локальным паролем в `docker-compose.yml`.
Тесты не читают этот файл автоматически; при смене пароля задайте `RFR_DB_PASSWORD`.

Для другой БД в zsh пароль можно ввести без отображения и сохранения в истории:

```zsh
read -rs 'RFR_DB_PASSWORD?MySQL password: '
export RFR_DB_PASSWORD
```

При смене адресов согласуйте конфигурации серверов, OAuth redirect URI
и `.env` интерфейса: настройки тестов сами их не изменяют.

Пример запуска с system property:

```bash
./gradlew :rfr-e2e:test --tests '*RegistrationTest' -Drfr.front.url=http://localhost:3001
```

Chromium должен соответствовать версии Playwright из `build.gradle`.
Для явной подготовки окружения используйте `:rfr-e2e:installPlaywright`.
