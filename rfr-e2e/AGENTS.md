# Модуль rfr-e2e

Общие правила находятся в [корневом AGENTS.md](../AGENTS.md), сценарии и устройство фикстур — в [README.md](README.md). Перед запуском прочитайте раздел [«Настройки тестов»](README.md#настройки-тестов): там описаны `TestConfig`, переменные окружения, параметры JVM и ввод пароля БД.

## Структура и окружение

Java-тесты находятся в `src/test/java/io/student/rangiffler/`: сценарии — в `test/`, Page Object — в `page/`, расширения JUnit и фикстуры — в `jupiter/`, доступ к БД — в `data/`. SQL и тестовые изображения находятся в `src/test/resources/`.

Все Page Object размещайте только в `src/test/java/io/student/rangiffler/page/` с пакетом `io.student.rangiffler.page`. Не создавайте параллельный каталог или пакет `ui/page` и не дублируйте страницы в других каталогах.

Используются JUnit Jupiter 6, Playwright Java и Allure. Настройки JUnit находятся в `src/test/resources/junit-platform.properties`; параллельный запуск отключён. Минимальный процент покрытия не настроен. Собственного серверного порта у модуля нет.

Для браузерных сценариев нужны MySQL и запущенные auth (`9001`), API (`8081`) и интерфейс (`3001`). Chromium должен соответствовать версии Playwright из `build.gradle`.

## Конфигурация и данные

- Для локальной MySQL из Docker Compose пароль задан в `TestConfig` по умолчанию. Для другой БД или при смене локального пароля задайте `RFR_DB_PASSWORD`. Учётной записи нужен доступ к `rangiffler-auth` и `rangiffler-api` на одном сервере MySQL. Тестовые параметры не перенастраивают запущенные сервисы.
- Для подготовленного пользователя используйте существующую связку `@User TestUser`, `UserExtension` и `UserFixture`; браузер и `Page` предоставляет `BrowserExtension`.
- В сценарии регистрации не используйте `@User`: пользователь должен появиться через UI. Следуйте `RegistrationTest`, который готовит только данные и удаляет созданную запись через `@AfterEach`.
- Фикстура удаляет созданные данные после теста. Не отключайте автоматическое закрытие `AutoCloseable` в JUnit Store; ошибка очистки должна оставаться видимой.
- Очистка разрешена только для точного логина формата `ui_registration_[0-9a-f]{32}`. Используйте существующую генерацию данных, не расширяйте область удаления ради нового сценария.
- SQL храните в `src/test/resources/sql/` и передавайте значения через параметры. Очистка обеих схем использует одно соединение и общую транзакцию; переключение клиента БД внутри callback не присоединяет его к этой транзакции.
- Page Object скрывают локаторы, действия и ожидающие проверки Playwright. Не переносите детали локаторов в сценарии.

## Правила тестов

Для создания и рефакторинга Page Object и переиспользуемых UI-компонентов используйте проектный навык `rfr-page-objects`. Перед такой работой прочитайте его [SKILL.md](../.codex/skills/java-playwright-page-objects/SKILL.md): он задаёт правила структуры, локаторов, разделения действий и проверок, ожиданий Playwright, шагов Allure и проверки компиляции.

- Называйте классы по шаблону `*Test`. Один тест проверяет один сценарий поведения.
- Предпочитайте одну содержательную проверку результата; несколько допустимы, если вместе описывают результат одного сценария и делают тест понятнее.
- Используйте общую подготовку и очистку, когда они уменьшают дублирование и сохраняют независимость тестов.
- При случайных данных обеспечивайте возможность повторить сбой. Ограничивайте ожидания тайм-аутами и освобождайте созданные ресурсы.
- Не обращайтесь к внешнему интернету и реальным пользовательским данным без необходимости. Явно указывайте использованное окружение и зависимости браузерных сценариев.
- При нестабильности теста сообщайте о ней и исследуйте причину в пределах задачи; повторный успешный запуск не подтверждает устранение причины.

## Подтверждение работы теста

Доказательство работы теста — успешный запуск соответствующей задачи `test` через Gradle Wrapper, например `./gradlew :rfr-e2e:test --tests '*RegistrationTest'`. Убедитесь, что нужный тест фактически выполнен и прошёл, а сборка завершилась с `BUILD SUCCESSFUL`. Компиляция, `--dry-run`, результат из кэша, `UP-TO-DATE` или пропущенный тест не подтверждают выполнение; при необходимости используйте `--rerun-tasks` для нового запуска. В отчёте указывайте команду и фактический результат. Если запуск заблокирован окружением, явно сообщайте об этом и не утверждайте, что тест работает.

## Команды из корня репозитория

- `./gradlew e2eTest` — запуск всего набора E2E через корневую задачу, зависящую только от `:rfr-e2e:test`. Тесты бэкенд-модулей не запускаются; серверы и БД должны быть запущены заранее. Для выбора отдельного класса используйте прямую задачу `:rfr-e2e:test --tests ...`.
- `./gradlew :rfr-e2e:installPlaywright` — отдельная установка Chromium перед первым запуском и после обновления Playwright; требует доступа к серверу загрузки, не является зависимостью тестов.
- `./gradlew :rfr-e2e:test --tests '*RegistrationTest'` — запуск выбранного класса.
- `./gradlew :rfr-e2e:test --tests '*ProfileTest' -Drfr.headed=true` — запуск с видимым браузером.
- `./gradlew :rfr-e2e:test` — запуск всего набора.

При выборе проверки учитывайте изменение: регистрация, вход, отрицательные сценарии входа или профиль. Запуск тестов создаёт и удаляет данные в настроенной БД; не направляйте их на общую среду без согласования.
