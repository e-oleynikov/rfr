# Page Object для Java и Playwright

Применяй эти правила к Page Object и их переиспользуемым UI-компонентам. Создание skill само по себе не означает запрос переписать существующие PO или добавить новые сценарии тестирования.

## Перед реализацией

Изучи инструкции проекта, существующие PO, конфигурацию URL и используемые Allure-интеграции. Уточняй только существенные неоговорённые решения по правилам проекта. Проверяй локаторы по доступному UI через Playwright MCP или по исходникам страницы; не выдумывай атрибуты. Не меняй стек тестов ради применения skill.

## Структура и переиспользование

- Объявляй классы страниц и UI-компонентов как `public final class`. Поля - `private final`
- Используй композицию вместо наследования: общую шапку, меню, форму или диалог выноси в отдельный компонент и передавай ему `Page` или корневой `Locator` через конструктор. Не создавай `BasePage` и не наследуй PO друг от друга.
- Храни `Page`, компоненты и локаторы в `private final` полях.
- Конструктор PO принимает `Page page` и не делает ничего, кроме присвоения `this.page = page` и инициализации остальных `private final` полей PO: локаторов и компонентов. Не добавляй в конструктор навигацию, действия с UI, проверки, ожидания, чтение данных страницы, подготовку тестовых данных или другую логику. Компонент может принимать `Page` или корневой `Locator`, сохраняя то же ограничение на работу конструктора.
- В каждой странице объявляй URL именно полем `public static String URL`. Формируй его из конфигурации соответствующего сервиса и пути страницы, например `TestConfig.frontUrl() + "/profile"`. Не заменяй поле приватным геттером или `public static final`; не меняй его в сценариях. Компонентам без собственного маршрута поле URL не требуется.
- Бери адреса сервисов из конфигурации проекта; не дублируй host и port в PO. Если нужного адреса в конфигурации нет, добавляй его по принятому в проекте механизму.

## Действия и проверки

- Полностью разделяй действия и проверки в обе стороны. Методы действий не вызывают методы проверок и не содержат assertions. Методы проверок не выполняют действий и не вызывают методы действий.
- `open()` только открывает URL. Предметные методы `should...` только проверяют конкретное ожидаемое состояние. Не вызывай их из `open()`, после клика или из конструктора следующего PO.
- Объединяй заполнение полей одной бизнес-формы в один метод с предметным именем: `fillRegistrationForm(...)`, `fillLoginForm(...)`, `fillProfileDetails(...)`. По имени метода должно быть понятно, какая форма заполняется или какое бизнес-действие выполняется. `fillForm(...)` — только условный пример группировки действий, а не требуемое имя метода. Не используй в реальном PO общие имена `fillForm(...)`, `fill(...)` или `setData(...)`, скрывающие назначение действия. Не заставляй тест вызывать цепочку отдельных сеттеров полей.
- Отправку формы выделяй в отдельный метод с предметным именем: `submitRegistration()`, `signIn()`, `saveProfile()`. `submit()` — только условный пример; фактическое имя должно объяснять бизнес-действие. Метод заполнения формы не нажимает кнопку отправки. Для другого бизнес-действия выбирай один предметный метод, не дроби его на клики без необходимости.
- Возвращай `this` для fluent-методов текущей страницы. Действие с переходом может вернуть объект следующей страницы, но не должно проверять его автоматически. Порядок действий и проверок явно задаёт тест.
- Если пользователь не потребовал иное, используй ожидающие Playwright conditions через `com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat(...)`: `isVisible()`, `hasValue(...)`, `hasText(...)`, `hasURL(...)`, `isEnabled()` и аналогичные проверки.
- Не создавай методы `checkPageLoaded()` и их аналоги (`waitForPageLoaded()`, `ensurePageLoaded()` и другие универсальные проверки готовности страницы), в том числе под другим именем. Используй web-first assertions для конкретного ожидаемого состояния: нужного элемента, текста, значения или URL. Не добавляй отдельный этап «страница загружена» перед действием или проверкой: Playwright автоматически ожидает готовность элемента к действию, а assertions — ожидаемое состояние. Предметные методы `should...` допустимы, если проверяют конкретный результат сценария, а не общую загрузку страницы.
- Не заменяй ожидающие проверки на `assertTrue(locator.isVisible())`, мгновенное чтение `textContent()` с JUnit-проверкой или ручные циклы ожидания. Не добавляй `Thread.sleep`, фиксированные задержки, клики, `fill`, навигацию или подготовку данных в методы `should...`.
- Метод проверки может содержать несколько связанных assertions, например URL, заголовок и ожидаемый логин. Он не должен менять состояние страницы.

## Allure и параметры

- Каждый публичный метод действия или проверки PO и UI-компонента обязательно помечай `@Step`. Конструкторы не являются шагами. Не создавай публичные технические методы для обхода этого правила.
- Пиши названия шагов на русском, начиная с понятного действия: «Открыть профиль», «Заполнить форму входа», «Проверить логин пользователя».
- Параметры логируются: каждый параметр метода попадает в текст шага через placeholder `@Step`, например `@Step("Заполнить форму входа {username}/{password}")`
- Логируй параметры через Allure: сохраняй параметры вызова шага и добавляй значимые несекретные значения в шаблон `@Step`, например `@Step("Проверить логин пользователя {username}")`. Не добавляй SLF4J ради дублирования шагов.
- Маскируй секретные параметры средствами Allure, например `@Param(mode = Parameter.Mode.MASKED)` для пароля. Не вставляй пароли и токены в текст шага, сообщения ошибок или `toString()` моделей. Маскирование параметра в интерфейсе Allure не удаляет исходное значение из файлов результатов: учитывай это при настройке автологирования вложенных Playwright-вызовов.
- Для составного аргумента формы используй модель данных с безопасным `toString()` либо явные параметры метода, чтобы в отчёте оставались понятные несекретные значения.

## Пример формы профиля

Пример показывает разделение ответственности; локаторы и маршрут адаптируй к фактической странице.

```java
import com.microsoft.playwright.Locator;
import com.microsoft.playwright.Page;
import com.microsoft.playwright.options.AriaRole;
import io.qameta.allure.Step;
import io.student.rangiffler.config.TestConfig;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

public final class ProfilePage {
  public static String URL = TestConfig.frontUrl() + "/profile";

  private final Page page;
  private final Locator firstname;
  private final Locator surname;
  private final Locator saveButton;

  public ProfilePage(Page page) {
    this.page = page;
    firstname = page.getByRole(AriaRole.TEXTBOX,
        new Page.GetByRoleOptions().setName("First Name").setExact(true));
    surname = page.getByRole(AriaRole.TEXTBOX,
        new Page.GetByRoleOptions().setName("Surname").setExact(true));
    saveButton = page.getByRole(AriaRole.BUTTON,
        new Page.GetByRoleOptions().setName("Save").setExact(true));
  }

  @Step("Открыть профиль")
  public ProfilePage open() {
    page.navigate(URL);
    return this;
  }

  @Step("Заполнить профиль: имя {firstname}, фамилия {surname}")
  public ProfilePage fillProfileDetails(String firstname, String surname) {
    this.firstname.fill(firstname);
    this.surname.fill(surname);
    return this;
  }

  @Step("Сохранить профиль")
  public ProfilePage saveProfile() {
    saveButton.click();
    return this;
  }

  @Step("Проверить имя {firstname} и фамилию {surname} в профиле")
  public ProfilePage shouldHaveName(String firstname, String surname) {
    assertThat(page).hasURL(URL);
    assertThat(this.firstname).hasValue(firstname);
    assertThat(this.surname).hasValue(surname);
    return this;
  }
}
```

## Проверка результата

Проверь соблюдение разделения действий и assertions, наличие `final`, поля URL и русских `@Step` с параметрами. Убедись, что общие элементы переиспользуются через композицию и пароль не попадает в текст шагов.

После создания или изменения PO обязательно запусти компиляцию тестов через Gradle Wrapper из корня проекта:

```bash
./gradlew :rfr-e2e:compileTestJava
```

Используй JDK 25. Проверка компиляции считается пройденной только после успешного завершения задачи (`BUILD SUCCESSFUL`); одной проверки синтаксиса или компиляции основного кода недостаточно. Исправь ошибки, вызванные изменениями PO, и повтори компиляцию. Если запуск блокирует окружение или внешняя зависимость, явно сообщи об этом и не утверждай, что компиляция прошла. В другом проекте используй соответствующую задачу `compileTestJava` его тестового модуля.

Запускай затронутый UI-сценарий, когда доступно его окружение. Сообщи, какие проверки выполнены, и обозначь фактические ограничения проверки.
